# 06 · 探索过程记录

本篇记录整个排查过程 —— **结论都在其他文档里，这一篇讲的是"怎么找到结论的"**。里面的方法比结论更通用。

---

## 阶段一：让同机的两个星际连上

### 起点

目标：在同一台 PC 上让两个星际 1.16.1 联机，一个自己操作，一个跑 Pluto AI。

现象：**UDP 和 IPX 都连不上。**

### 第 1 步：不猜，先量

"连不上"这个描述没有信息量。先做的是**直接测端口**：

```python
# 6112 端口能不能被两个 socket 同时绑定？
6112  直接 bind → 10048(已被占用)    带 SO_REUSEADDR → 10013(拒绝)
6113  直接 bind → OK
```

`10013`（WSAEACCES）这个错误码很关键 —— 在 Windows 上它的含义是：

> 已存在的那个绑定**没有设置 SO_REUSEADDR**。

也就是说星际是**独占绑定** 6112 的：**同机第二个实例永远绑不上**。

### 第 2 步：抓到真实画面

光看日志还不够，直接**抓取游戏窗口内容**（用 `PrintWindow` API，不打扰用户操作），看到了确凿证据：

> 实例 B 停在「选择连接」界面，弹着红框：**「无法初始化网络提供商。」**

列表里只有：Battle.net / 本地局域网(IPX) / 调制解调器 / 直接电缆连接 / 本地局域网(UDP)。**没有传说中的 "Local PC"** —— 所以 `bwapi.ini` 里 `lan_mode = Local PC` 那种写法在 1.16.1 上用不了。

### 第 3 步：验证一个流传的说法

网上流传"改注册表 `Game Data Port` 能换 LAN 端口"。查了，**对 LAN 无效**：

- 注册表时间戳显示用户把它设成了 `6114`，实例 B 也是在设置**之后**才启动的
- 但日志里星际绑定的始终是 **6111/6112**，`6114` 从头到尾没出现过
- 结论：该键只影响 Battle.net，LAN 端口是写死的

**→ UDP 这条路在同机上走不通，转向 IPX。**

### 第 4 步：IPX 的日志分析

IPXWrapper 的日志是 verbose 级别、两个进程写同一个文件，所以能直接看出**两个实例到底做了什么**。

分析 21 个会话后发现：

- 每个会话都是「枚举网卡 → bind 6112 → 发送 → 关闭」，**一次 `recvfrom` 都没有** —— 从未真正通信
- **所有会话用的节点号完全相同**（`B0:A4:60:DA:7F:23`，取自 Wi-Fi 网卡 MAC）

节点号重复 = 星际会把对方发来的包当成自己发的丢掉。

**根因 1：`HKCU\Software\IPXWrapper\<网卡MAC>` 是共享的，两个实例读到同一份配置。**

### 第 5 步：给第二个实例独立节点

做法：**独立 Windows 账号** → 独立 HKCU → 独立节点号。

同时发现一个有意思的事实：星际的**单实例检查是按用户隔离的** —— 实测同一个 exe：

```
以 Administrator 启动 → 8 秒内自动退出（被已有实例挡住）
以新账号启动        → 存活 ✅
```

所以第二个实例甚至不需要 Chaoslauncher 的多开补丁。

### 第 6 步：还是不行 —— 读源码

节点号已经不同了，还是连不上。这时候去读了 IPXWrapper 的源码，找到 `_complete_bind()`：

```c
if((sock->sock_mut = _open_socket_mutex(
    ntohs(sock->addr.sa_socket), !(sock->flags & IPX_REUSE))))
```

再看 `_open_socket_mutex()`：

```c
snprintf(mutex_name, sizeof(mutex_name), "ipxwrapper_socket_%hu", socket);
HANDLE mutex = CreateMutex(NULL, FALSE, mutex_name);
if(GetLastError() == ERROR_ALREADY_EXISTS && exclusive) return NULL;  // ← 绑定失败
```

**互斥体名字是纯字符串，不含用户/进程信息** → 同一登录会话里**跨用户照样互撞**。星际固定绑 socket 6112，第二个实例拿不到。

**而这条失败分支一行日志都不打** —— 日志里只有：

```
bind(3672, .../6112)
sendto() on unbound socket, attempting implicit bind     ← 没有 bind address 行
```

再回头对比成功的会话：

```
bind(5008, .../6112)
bind address: 00:00:00:01/B0:A4:60:DA:7F:23/6112        ← 有这一行
```

**这一处差异就是根因。** 而且注意：同一个实例在别的时刻又能成功绑定 6112（那时另一个实例已退出）—— 完美印证了"互斥体被占"。

**根因 2：IPXWrapper 的具名互斥体跨进程跨用户互撞。**

### 第 7 步：改名字，不改逻辑

没有去改代码，而是**只改了互斥体的名字**：

```
"ipxwrapper_socket_%hu"  →  "jpxwrapper_socket_%hu"
```

让第二个实例从**影子目录**加载这份改过的 DLL（16 进制编辑器级别的 1 字节改动）。这样：

- 两边互斥体命名空间独立 → 都能绑 6112
- 各自进程内语义完全不变（单进程内的互斥仍然生效）
- 原 DLL 一个字节没动

影子目录用**目录联接 + 硬链接**搭建，零额外磁盘占用。

**结果：连上了。**

## 阶段二：把 Pluto 搬上重制版

### 起点

社区有人做了把 Pluto 接到重制版的桥接。但它是**实验性项目**，且**原仓库已下架**。

### 第 1 步：先验证版本匹配

拿到项目后第一件事不是运行，而是**核对哈希**：

```
重制版 x86\StarCraft.exe  32DBBDD0…  ← 与项目要求的 32dbbdd… 逐位吻合
pluto_infer.exe            AD880D8B…  ✓
pluto_weights.bin          00B400EA…  ✓
```

版本对得上，才有必要继续。

### 第 2 步：搞清楚它怎么工作

读源码发现关键一点：

```
scr-loader.exe <PID> <DLL>
```

**它是按 PID 注入到已运行的进程**，而不是自己启动游戏。

这直接决定了国内环境的整合思路：**让 KK 平台去启动游戏**（它负责房间和联网），我们只负责把 AI 挂上去。

### 第 3 步：国内环境的第一个坑 —— x86

桥接只支持 **x86** 客户端，而 KK 平台默认拉起的是 `x86_64\starcraft.exe`。

查 KK 的配置找到了开关：

```ini
<KK目录>\config\custom\platform.ini
[SCGame]
SCRRootDir=G:\StarCraft\x86
```

改指向 x86 即可。

### 第 4 步：第二个坑 —— 只认 Melee

第一次联机测试：**打电脑时 Pluto 生效，真人进来就不生效。**

日志直接给出了答案：

```json
{"stage":"session_skipped","reason":"unsupported_game_type",
 "game_type":15,"game_type_name":"Top vs Bottom","self":2}
```

对照源码 `session.h`：

```c
if(s.game_type!=2 && !(challenge && (s.game_type==3 || s.game_type==15)))
    return "unsupported_game_type";
```

**普通联机模式只接受 Melee（game_type=2）**，Top vs Bottom（上方vs下方）和 FFA 只有挑战模式才放行。

改成 Melee、2 名真人 → 成功。

### 第 5 步：第三个坑 —— 环境变量传不进去

日志里反复出现：

```
Pluto: this machine can't keep up (inference ~88 ms/step, stalling the game ~42 ms per decision)
```

联机需要 `BWRL_STRADDLE=1` 来对齐推理节奏和网络锁步时钟。但这两个变量是**推理引擎从环境变量读的**，而联机时游戏是 KK 拉起来的 ——

**游戏继承的是 KK 的环境变量。** 用 `setx` 设了但没重启 KK，游戏照样拿不到。

解法：**用带环境变量的启动器启动 KK 本身。**

### 第 6 步：遗留问题

对局打到末期会出现访问违例崩溃（`0xC0000005`），崩溃地址偏移在不同机器上一致 —— 是可复现的上游 bug。桥接崩溃后彻底失效，第二局自然没有 AI。

这是实验性项目的固有代价，上游仓库已下架，只能靠 `-Watch` 模式每局自动重注入绕过。

## 方法论总结

回头看，有用的就四条：

1. **先量，不要猜。** 端口能不能绑、包能不能通，写几行代码就能测出来，比搜帖猜半天快得多。
2. **对比成功与失败的记录。** 两次 `bind` 日志只差一行，根因就在那一行里。
3. **现象要具体。** "连不上"没法定位；"进选连接界面弹无法初始化网络提供商"能立刻定位到端口。
4. **上游开源就读源码。** 本项目的**两个根本原因都是读源码找到的**，光看现象永远找不出来 —— 尤其是第二个，它连错误日志都不打。
